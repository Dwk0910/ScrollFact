# 2026 C.O.D.E. 트랙 3 출품 준비 분석

**팀 확인:** 오남고등학교 **트리오남**은 공식 본선 진출팀 명단의 트랙 3(상상)에 등재되어 있다. 2026년 9월 21일 공지 붙임 3쪽에서 팀대표는 ‘김 ○ 완’으로 표기된다. [공식 명단](references/finalist-teams-2026-09-21.pdf), [11월 1일 코칭 준비안](coaching-2026-11-01.md).

정리일: 2026년 11월 1일. 주제를 다시 정하기 전에 대회 목적, 요구 산출물, 평가 기준과 검증 방법을 정리한다. 현재 제품 주제는 확정 전이며, 원래 ScrollFact의 문단별 읽기·요약·근거 확인·스크롤 연동을 개선하는 경로도 후보에 포함한다.

이 대회에서 증명해야 할 것은 **온라인 대화가 끊기는 구체적인 원인을 발견하고, AI의 도움으로 사용자가 사실·맥락·다른 관점을 확인하여 스스로 다음 행동을 선택할 수 있게 했는가**다. 이 문장은 안내문과 강연을 종합한 기획 해석이다. 공식 문제, 운영 요건과 우리의 예측은 아래에서 구분한다.

**해석 보완:** 읽기·정보 검증을 통해 간접적으로 기여하는 서비스도 대회 범위에 들어간다. 공식 유형별 문제는 정보 검증과 팩트체크를 주제 예시로 제시하고, 결선 안내문은 읽는 중의 사용 맥락도 인정한다. 댓글 순화나 대화 개입 기능을 추가해야 한다는 요구는 없다. 원래 ScrollFact의 문단별 분석·출처 연결·스크롤 연동은 유지할 수 있다. 아래에서 효과 검증을 요구하는 것은 제품 방향을 제한하기 위해서가 아니라, 관찰한 효과보다 큰 주장을 피하기 위해서다.

## 대회 목적과 트랙의 범위

대회는 디지털새싹 문제해결 경진대회 「2026 C.O.D.E.」다. 교육부·16개 시도교육청이 주최하고 한국과학창의재단이 주관한다. 실생활의 문제를 발견하고 AI·디지털 기술로 해결하는 프로젝트 경험을 목적으로 한다. 같은 학교 학생 3인과 담당교사 1인으로 구성하며, 본선 45팀 선정이 공지됐다. [공식 모집 공지](https://newsac.kosac.re.kr/public/boards/1089/posts/62023?category=1101), [본선 선정 공지](https://newsac.kosac.re.kr/public/boards/1089/posts/62140?category=1101&page=1).

우리의 트랙은 **트랙 3 상상 자유 아이디어 경연**이며 출제 기관은 라쿠텐심포니코리아다. 키워드는 **디지털 공존 — 존중·균형·신뢰·소통**, 슬로건은 **세상을 이롭게 하는 소통**이다. ‘자유’는 이 문제 안에서 해결 방식과 기술을 자유롭게 선택한다는 뜻으로 이해해야 한다. [결선 안내문, 문제 안내](references/track3-final-guide.jpg).

공식 문제는 공격적 표현, 오해와 허위정보로 생기는 사회적 갈등을 줄이고 서로 다른 생각을 가진 사람들이 건강하게 소통하도록 돕는 서비스를 요구한다. 다음 조건도 명시한다.

- 실제 갈등 상황과 대상 사용자를 정의한다.
- 대화가 단절되는 원인을 찾아 오해를 줄이고 상호 이해를 돕는다.
- AI를 활용하며, 요약·맥락 분석·표현 전환·정보 검증·중재 등은 선택할 수 있다.
- 특정 정치적 입장이나 개인·집단을 평가·분류하는 서비스는 지양한다.
- 실제 개인정보·비공개 대화를 쓰지 않고 가상 또는 공개 데이터를 활용한다.
- 기능 수보다 공감, 책임 있는 AI 활용, 실제 사용 가능성을 중시한다.

출처: [결선 안내문, 문제 안내와 필요 요건](references/track3-final-guide.jpg).

### 문제 범위를 해석할 때 주의할 점

**건강한 소통은 의견 일치를 의미하지 않는다.** 서로 다른 조건과 근거를 이해한 뒤에도 의견이 다를 수 있다. 사용자가 다른 입장을 유지하는 경우까지 정상적인 결과로 취급하는 것이 문제 설명에 부합한다는 해석이다.

**근거 확인은 대화에 어떤 영향을 주는지까지 연결해야 한다.** 정확한 문장을 찾았다는 사실만으로 오해가 줄었다고 볼 수 없다. 누구의 어떤 오해가 줄고, 어떤 선택이 가능해지는지를 설명해야 한다. 강연 16:03~17:06도 사실을 지적하는 것만으로 감정이나 악의적 의도가 해결되지 않는다고 설명한다. [전사문](references/presenter-transcript.txt).

**‘누구나 설치할 서비스’는 장기적인 목표로 남긴다.** 첫 검증에서는 한 상황에서 반복적으로 발생하는 불편과 갈등을 구체화해야 한다. 실제 사용 가능성 항목은 실제 플랫폼·상황에 적용되는 흐름과 사용 이유를 묻는다. 모든 사이트 지원이나 모든 연령대 확보를 필수로 요구하지 않는다. [결선 안내문, 평가안](references/track3-final-guide.jpg).

**제품을 두 가지 형식으로 만들어야 한다는 요구는 없다.** ‘택1’이므로 복수 형식의 제출 허용 여부나 추가 평가상 이점도 현재 자료에서 확정할 수 없다. 웹과 확장을 모두 만들더라도 같은 문제 해결을 더 잘 입증하는 이유가 있어야 한다는 것이 우리의 준비 전략이다.

**가상 입력 데이터와 고정된 AI 출력은 구분해야 한다.** 가상 데이터는 안내문에서 허용한다. 실제 AI 없이 준비된 결과만 전환하는 화면은 현재 아이디어 탐색에는 유용하지만, 결선에서 AI 기능이 실제 작동한다는 증거로 제시하기 어렵다는 해석이다. 캐시·녹화·예상 응답을 사용한 부분은 실시간 동작과 구분해서 설명한다. 이는 특정 AI 공급자를 쓰거나 모든 처리를 현장에서 새로 수행해야 한다는 공식 규정은 아니다.

### 문제 인식과 공감 20점

‘인터넷에 갈등이 많다’는 문제 규모 설명이다. 심사 기준에 더 직접 대응하려면 **누가 무엇을 보고 어떻게 해석했고, 어느 지점에서 상대와 대화하기 어려워졌는지**를 밝혀야 한다. 사람의 행동을 모두 부주의나 악의로 설명하면 서로 다른 관점을 이해한다는 목표와 어긋날 수 있다.

예상 확인 질문은 “사용자의 실제 경험을 어떻게 확인했는가?”, “그 원인을 해결하면 어떤 행동이 달라지는가?”다. 공감 인터뷰나 공개 사례 분석에서는 관찰한 내용과 팀이 추측한 원인을 나누어 기록한다. 몇 명의 의견을 전체 사용자 수요로 확대하지 않는다.

### 창의성과 차별성 20점

화면의 새로움이 문제 해결의 새로움을 보장하지는 않는다. AI 요약·출처 링크·표현 순화라는 기능명은 공식 예시에도 등장하므로, 구현 사실만으로 차별성을 주장하기 어렵다. **어떤 순간에, 어떤 정보를, 어떤 행동으로 확인하게 해서 기존의 장벽을 줄이는지**가 차별성의 설명이 되어야 한다.

예상 질문은 “범용 AI에 복사해서 물어보는 것과 어떤 차이가 있는가?”, “기존 플랫폼의 기능으로 해결하기 어려운 이유는 무엇인가?”다. 경쟁 서비스 조사는 다음 주제 후보가 생긴 뒤 실제 비교 대상을 확인한다. 현 단계에서 ‘세계 최초’나 ‘기존에 없다’를 주장하지 않는다.

### 책임 있는 AI 활용과 시연 완성도 25점

이 항목은 AI의 목적 적합성, 사용자 선택권·출처 표시 등 책임 있는 설계와 시연 완성도를 함께 묻는다. 25점을 모델 성능만의 점수, 또는 윤리 설명만의 점수로 해석하면 안 된다.

예상 질문은 “AI가 틀렸을 때 사용자는 알아차릴 수 있는가?”, “원문이 그 주장을 실제로 뒷받침하는가?”, “판단을 보류할 수 있는가?”다. 출처가 붙어 있다는 사실과 출처가 결론을 지지한다는 사실을 구분해야 한다. URL뿐 아니라 인용 위치, 전후 맥락, 시점·적용 조건이 연결되어야 근거를 확인할 수 있다.

또한 의견·감정·검증 가능한 사실을 한 점수로 합쳤다면 그 점수의 의미를 설명해야 한다. 예전 신뢰도 게이지는 자동으로 다음 기획에 계승하지 않는다. 점수가 반드시 금지된다는 규정은 없지만, 점수만 보고 사용자가 판단을 끝내게 만드는 구조는 출제 의도와 긴장이 있다는 분석이다.

### 실제 사용 가능성 15점

사용자가 원문을 수동으로 수집하고, 별도 페이지에 옮기고, 여러 설정을 해야 효과가 생긴다면 그 비용부터 검증해야 한다. 좋은 개입도 읽기·쓰기 흐름을 자주 방해하면 사용 이유가 약해질 수 있다.

예상 질문은 “처음 설치한 사람이 설명 없이 사용할 수 있는가?”, “매번 이 작업을 할 이유가 있는가?”, “이 사이트에서 실제로 동작하는가?”다. 데모 전용 데이터나 페이지에 의존하는 부분, 외부 플랫폼에서 아직 구현하지 않은 부분은 정확히 구분해 설명한다. 전 플랫폼 지원을 약속하기보다 실제 검증한 범위를 보여주는 편이 설득력 있다는 판단이다.

### 과정 참여와 발표 및 팀워크 20점

창의성과 같은 20점이므로 결과 화면만 준비해서는 대응하기 어렵다. 이 항목은 멘토링 참여, 아이디어 발전, 협업과 비전문가도 이해할 수 있는 발표를 포함한다. 코디네이터 멘토링 3회 이상과 통합 멘토링 참여를 구분해 기록하고, 팀의 실제 완료 내역을 확인해야 한다.

앞으로 남길 기록은 날짜, 발견한 문제, 검토한 대안, 테스트에서 관찰한 행동, 받은 피드백, 바꾼 이유, 담당자다. 코드 작성량만으로 기여를 설명하지 않는다. 조사·설계·구현·검증·발표의 기여를 함께 남긴다. 이미 했던 실험은 남아 있는 기록으로만 복원하고, 관찰하지 않은 사용자 반응을 만들어 넣지 않는다.

## 심사위원이 특히 확인할 것으로 예상되는 지점

예측의 강도는 공식 요건과의 연결 정도다. 특정 심사위원의 취향을 확인한 결과가 아니다. 초기 모집요강의 심사위원 구성 안내는 **서류심사** 대상이므로 이를 결선 심사위원 명단이나 구성으로 단정하지 않는다.

| 예상 쟁점 | 예상 근거와 강도 | 대비할 설명 또는 장면 |
| --- | --- | --- |
| AI에게 판단을 넘겼는가 | 강함. 공식 문제 설명·사용자 선택권 요구·강연에서 반복 | 원문 확인 후 수용·거절·보류하는 사용자 행동 |
| 실제 AI와 기능이 작동하는가 | 강함. 실제 동작 결과물과 입력 비교 요구 | 서로 다른 입력에서 근거와 결과가 바뀌는 전체 흐름 |
| 대화 개선과 직접 연결되는가 | 강함. 공감·차별성·문제 정의 항목 | 어떤 오해가 줄거나 어떤 이해가 새로 가능해졌는지 설명 |
| 근거가 관련 있고 충분한가 | 강함. 출처 확인·책임 있는 AI·강연의 검증 가능성 | 원문 문장과 조건, 확인할 수 없는 부분을 함께 제시 |
| 불필요한 개입을 하지 않는가 | 중간. 사용 가능성과 판단권에서 도출 | 정당한 비판·견해 차이에 과도하게 교정하지 않는 사례 |
| 오류·지연에 대응하는가 | 중간. 시연 완성도·백업 영상·강연의 실패 사례 | 기다리는 이유, 실패 안내, 다시 시도·원문 복귀 |
| 작은 팀이 설명하고 유지할 수 있는가 | 중간. 팀워크·실제 사용 가능성에서 도출 | 구현 범위, 담당 역할, 주요 결정과 남은 한계 |
| 복수 산출물·특정 모델·코드 양이 유리한가 | 현재 자료로 예측할 근거 부족 | 이에 점수를 가정해 개발 범위를 늘리지 않음 |

## 심사에 보여줄 증거와 자체 검증 계획

이 절은 **팀을 위한 검증 제안**이다. 추가 제출 의무가 아니다. 공식 요구인 2~3개 비교 입력은 선정할 주제에 맞춰 준비하고, 자체 검증은 실패와 비개입 사례까지 넓힌다.

| 검증 질문 | 확인 방법 | 결과를 해석할 때의 한계 |
| --- | --- | --- |
| 근거를 정확히 연결했는가 | 인용문 존재, 주장 지지 여부, 빠진 조건·시점, 원문 위치를 사람이 대조 | URL 연결 성공만으로 사실 확인 성공이라고 세지 않음 |
| 원문과 상대 관점을 충실히 다뤘는가 | 요약의 의미 변화, 빠진 반대 조건, 사실과 해석의 혼합을 검토 | AI가 만든 평가만으로 AI를 채점하지 않음 |
| 사용자의 이해를 도왔는가 | 사용 전후에 주장·근거·불확실한 점을 본인 말로 설명하게 함 | 의견 변화나 동의 비율을 이해도와 동일시하지 않음 |
| 선택권이 실질적으로 남았는가 | 제안 거절·보류·원문 유지가 실제로 가능한지 관찰 | ‘계속’ 버튼 하나만으로 자율성을 입증했다고 보지 않음 |
| 일상 사용의 부담을 줄였는가 | 필요한 조작, 완료 시간, 중단·복귀와 방해 경험 기록 | 적은 참가자의 결과를 전체 서비스 효과로 일반화하지 않음 |
| 스크롤 조작이 도움을 줬는가 | 같은 정보를 일반 링크 탐색과 스크롤 방식으로 각각 확인 | 정보 내용·과제 차이와 순서 효과를 줄여 비교 |

자체 테스트에는 적어도 다음 성격의 사례가 필요하다. 숫자는 공식 개수가 아니라 테스트 범위 제안이다.

1. **도움이 필요한 경우:** 관련 근거나 맥락을 확인하면 실제로 오해가 풀릴 여지가 있는 입력.
2. **개입을 줄여야 하는 경우:** 예의 있는 반대 의견, 정당한 비판, 문맥 속 인용 등.
3. **확정할 수 없는 경우:** 정보 부족, 출처 충돌, 원문 삭제·변경 등.
4. **기술적으로 실패하는 경우:** 분석 지연, 호출 실패, 근거 위치 탐색 실패 등.

초기 사용자 검증에서는 소수의 동의한 참가자에게 가상 상황을 보여주고 식별정보 없는 관찰 결과를 남길 수 있다. 이 검증으로 실제 사회적 갈등 감소를 입증했다고 발표하지 않는다. 확인 가능한 주장은 ‘참가자가 근거를 찾는 데 도움이 됐다’, ‘오해한 조건을 설명할 수 있었다’처럼 측정한 행동의 범위로 한정한다.

## ScrollFact에서 남길 설계 조건

**스크롤은 대회 필수 요건이 아니라 우리가 선택한 제품 정체성이다.** 따라서 스크롤을 유지하려면 사용자의 이해와 근거 확인에 어떤 역할을 하는지 증명해야 한다. 아직 특정 화면 구조나 제품 주제를 확정하지 않는다.

다음은 이후 후보를 판단할 우리의 조건이다.

- 읽던 위치와 근거의 위치를 연결하고, 확인한 뒤 원래 맥락으로 돌아갈 수 있다.
- 사용자가 스크롤로 무엇을 살펴볼지, 어느 깊이까지 확인할지 통제할 수 있다.
- 원문과 AI 해석을 구별하고, 근거가 없는 연결은 확정된 사실처럼 제시하지 않는다.
- 사용자의 이동·취소·복귀 의사를 보존한다. 자동 이동을 쓴다면 즉시 멈출 수 있어야 한다.
- 스크롤 위치나 머문 시간만으로 ‘읽었다’, ‘이해했다’, ‘동의했다’를 판정하지 않는다.
- 키보드 등 대체 조작을 마련해 같은 근거를 확인할 수 있게 한다.

판별 질문은 하나다. **이 제품에서 스크롤을 없애면, 사용자가 근거와 맥락을 확인하는 방식에 중요한 손실이 생기는가?** 변화가 화면 효과에만 머문다면 다음 후보에서 스크롤의 역할을 다시 설계해야 한다.

이는 특정 댓글 예시, 후기 비교, 페이지 전체 신뢰도 점수, 게시 전 경고창을 유지한다는 뜻이 아니다. 기존 데모는 실험 기록으로 보관하고 주제 선택의 제약으로 삼지 않는다.

12분 발표에 필요한 내용을 넣기 위한 예시 시간 배분이다. 공식 지정 순서나 분 단위 배분은 아니다. 별도 3분은 심사위원 피드백 시간이다.

## 다음 기획 단계로 넘어가는 순서

원래 ScrollFact를 개선하는 경로도 후보에 포함한다. 기존 제품을 폐기해야 한다는 결론은 내리지 않았다. 아래 절차에서 비교할 것은 원래 제품의 개선과 새로운 문제 접근 모두다.

현재 단계의 산출물은 대회 해석과 평가 기준이다. 다음에는 다음 순서로 문제를 좁힌다.

1. **문제 상황 수집:** 특정 예시 하나에 고정하지 않고, 반복되는 온라인 대화 단절의 순간을 관찰한다. 사용자·맥락·원인·현재 해결 방법을 기록한다.
2. **후보 비교:** 대회 목적과 직접 연결되는지, 실제 불편이 있는지, 확인 가능한 근거가 있는지 비교한다.
3. **스크롤 역할 검증:** 각 후보에서 스크롤이 근거 탐색과 이해를 어떻게 바꾸는지 먼저 설명한다.
4. **작은 조작 데모:** 남은 후보를 같은 완성도로 체험한다. 한 후보에 많은 기능을 먼저 붙여 선택을 유도하지 않는다.
5. **주제 선택과 구현 범위 확정:** 사용자 반응과 구현 가능성을 바탕으로 핵심 기능, AI 역할, 결과물 형식, 검증 계획을 정한다.

다음 후보에는 아래 질문에 답한 짧은 문제 정의가 있어야 한다. 이것은 새 공식 채점표가 아니라 팀의 기획 기준이다.

| 질문 | 필요한 답 |
| --- | --- |
| 누구의 언제 생기는 문제인가 | 실제로 떠올릴 수 있는 사용자와 사용 순간 |
| 대화는 왜 어려워지는가 | 관찰한 원인과 아직 검증하지 않은 가설의 구분 |
| 근거 확인이 어떤 도움을 주는가 | 확인 대상과 확인 뒤 가능한 행동 |
| AI는 무엇을 맡는가 | 사람이 검토할 수 있는 작업과 실패 시 처리 |
| 스크롤은 왜 필요한가 | 일반 탐색과 비교되는 구체적 역할 |
| 사람에게 어떤 결정이 남는가 | 수용·거절·보류 등의 실제 선택 |
| 무엇을 시연하고 검증할 것인가 | 한 번의 완결된 흐름, 비교 입력과 관찰 지표 |

## 원래 ScrollFact와 대회 요구의 접점과 긴장

이 절은 2026년 11월 1일 사용자의 문제 제기를 반영한 비교다. 원래 제품의 실용성, 대회 적합성, 구현 상태, 실제 효과는 각각 확인해야 한다. 대회와 잘 맞는다는 사실만으로 효과가 입증되지는 않고, 모든 갈등을 해결하지 못한다는 이유로 읽기 도구의 가치를 부정할 수도 없다.

| 원래 ScrollFact의 요소 | 대회와의 관계 | 실제로 풀어야 할 문제 |
| --- | --- | --- |
| 스크롤에 맞춰 현재 문단의 분석 표시 | 잘 맞음. 읽는 중 정보·맥락 확인이라는 사용 순간이 명확함 | 확인 과정이 원문 읽기를 방해하지 않는지 검증 |

### 정량 평가에서 먼저 정할 것

현재 [백엔드 API 명세](../../frontend/docs/backend-api.md)는 점수를 0~100 정수와 백엔드의 종합 평가로 정의한다. 이 계약만으로는 80점이 참일 확률인지, 확인된 주장의 비율인지, 출처의 품질인지 알 수 없다. 점수 의미를 제품·분석 단계에서 정해야 한다는 뜻이며, 실제 분석기의 정확도를 검증했다는 뜻은 아니다.

출처를 함께 보여주는 것은 필요하지만, 임의로 산출한 숫자를 정당화하지는 못한다. 평가 기준을 먼저 정의하고 기준별 판정이 사람의 검토와 어느 정도 일치하는지 확인해야 한다. ‘근거 충실도’처럼 이름을 바꾸기만 해도 이 문제가 해결되지는 않는다. 문단 안에 복수의 주장·의견이 있다면 내부 분석 단위와 화면의 읽기 단위를 구분할 필요도 있다.

예를 들어 ‘확인 대상 주장 3개 중 자료가 지지하는 주장 2개, 확인할 수 없는 주장 1개’는 정의와 근거를 확인할 수 있는 요약 방식이다. 이것을 곧바로 ‘진실일 확률 67%’나 ‘글 전체 신뢰도 67점’으로 해석해서는 안 된다. 이 예시는 설계 선택의 비교용이며 구현 변경 결정이 아니다.

### 간접 효과를 뒷받침하는 연구와 한계

관련 연구는 간접 개입의 가능성을 뒷받침하지만, ScrollFact의 효과를 입증한 것은 아니다.

**추가 조사:** 적대감·공격적 공유·댓글까지 검토한 [팩트체킹과 대인 갈등 심층 조사](fact-checking-and-conflict.md)를 함께 읽어야 한다. 사실 지식이 개선돼도 적대감이 줄지 않은 실험, 공개 정정 이후 공격적인 콘텐츠 재공유가 늘어난 실험, 특정 오해 교정에서 긍정적인 결과를 얻은 실험이 함께 존재한다. 아래의 믿음·공유 품질 연구만으로 ‘팩트체킹이 대인 갈등을 줄인다’고 결론 내릴 수 없다.

- **사실에 대한 믿음:** Porter와 Wood의 2021년 4개국 실험은 팩트체크가 잘못된 정보에 대한 믿음을 줄였고, 다수의 효과가 2주 넘게 남았다고 보고한다. 대인 갈등 감소를 그 결과와 동일시하지 않는다. [연구 초록](https://pubmed.ncbi.nlm.nih.gov/34507996/).
- **공유 행동:** Pennycook 등의 2021년 연구는 정확성에 주의를 돌리는 개입이 이후 공유되는 뉴스의 품질을 높였다고 보고한다. 이 개입은 문단별 신뢰도 점수나 스크롤 UI와 다르므로, 우리의 설계에도 동일한 효과가 있다고 전제할 수 없다. [Nature 논문](https://www.nature.com/articles/s41586-021-03344-2).
- **대화 경험:** Argyle 등의 2023년 연구는 AI의 표현 제안이 보고된 대화의 질과 상호성, 말투를 개선했지만 정책 태도를 체계적으로 바꾸지는 않았다고 보고한다. 표현 개선도 측정된 결과와 그 범위를 구분해서 설명해야 한다. [연구 초록](https://pubmed.ncbi.nlm.nih.gov/37788311/).

원래 ScrollFact에 대해 검증할 가설은 ‘근거 확인의 부담 감소 → 잘못된 전제·누락된 조건 인식 → 부정확한 인용·공유 감소 → 그로 인한 오해와 충돌 일부 감소’다. 각 연결은 검증 대상이다. 이미 사실을 알면서도 이해관계나 가치관 때문에 대립하는 경우, 상대를 공격하려는 의도가 있는 경우까지 해결한다고 약속하지 않는다.

### 제품의 유지와 대회 검증 범위

현재 판단으로는 문단별 읽기·요약·근거 확인·스크롤 연동이라는 원래 제품 경험을 유지할 이유가 있다. 추가 댓글 기능이 대회 적합성을 보장하지도 않는다. 우선 확인할 것은 기존 경험만으로 근거 확인을 쉽게 하고 잘못된 이해를 줄일 수 있는지다.

검증은 일반 원문 읽기, 요약 제공, 문단별 근거 연결을 비교하는 방식으로 설계할 수 있다. 시간뿐 아니라 조건·예외의 정확한 설명, 원문이 지지하지 않는 주장에 대한 인용 여부, 모르는 부분을 구분하는지 관찰한다. 숫자 게이지의 효과는 같은 근거·설명에서 게이지 유무를 비교해 별도로 살필 수 있다. 근거 확인 없이 숫자를 따라 잘못 확신하는 현상도 함께 확인한다.

이로써 읽기와 근거 확인의 유용성을 평가할 수 있다. 실제 갈등 감소까지 주장하려면 상대방과의 상호작용이나 후속 행동을 추가로 관찰해야 한다. 제품이 일상적인 읽기 도움을 제공하고, 대회에서는 그중 오해와 관련된 사용 상황을 검증하는 구성이 가능하다.

## 운영 일정과 참여 조건

결선 안내문에는 트랙 3 결선이 **2026년 12월 13일 일요일 서울 DDP 아트홀**에서 열린다고 적혀 있다. 남은 일정으로 11월 코디네이터 멘토링·중간 점검·발표 리허설, 발표자료·백업 영상·전시물 사전 제출이 안내되어 있으며 세부 기한은 별도 공지다. 팀당 15분 중 발표는 12분, 심사위원 피드백은 3분이다. 발표 종료 5분 전 안내, 12분 종료 조건을 반영해 연습한다. [결선 안내문](references/track3-final-guide.jpg).

같은 안내문은 멘토링과 결선 참여의 중요성, HDMI 연결 기준, 인터넷이 필요한 경우 오프라인 백업 준비를 알린다. 팀 중도 이탈은 평가에 불이익이 있을 수 있다고 명시한다. 결과물 저작권은 참가팀에 있고 대회 홍보·성과 확산 활용 조건도 안내되어 있으므로, 제출 전에는 원문과 최신 운영 공지를 함께 확인한다.

시상은 트랙 참가 15팀 전원을 대상으로 대상 1팀, 금상 2팀, 은상 2팀, 동상 10팀으로 안내되어 있다. 대상은 교육부장관상과 기업 탐방·멘토링 등의 후속 지원이 제시되지만, 상품·지원 세부사항은 변경 가능하다고 되어 있다. 수상 가능성을 이 구성만으로 추정할 수는 없다. [결선 안내문, 시상 안내](references/track3-final-guide.jpg).

## 준비 상태와 남은 확인

자료 분석과 원문 보관은 완료했다. 새 주제·산출물 형식·핵심 기능은 아직 결정하지 않았다. 애플리케이션 코드나 기존 데모는 이 분석 때문에 변경하지 않았다.

발표자료·영상·전시물 마감과 규격, 확정 평가표, 멘토링 인정 횟수는 후속 안내 확인이 필요하다. 이 확인을 기다리는 동안 문제 관찰과 후보 비교는 진행할 수 있다. 실제 메일 발송이나 운영사무국 문의는 수행하지 않았다.
