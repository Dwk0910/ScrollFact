# ScrollFact AI 인수인계

## 2026-11-24 댓글을 상단 관점 게이지에 통합

사용자는 단순 댓글 목록이 아니라 댓글을 입장·이유별로 분류한 상단 게이지가 핵심이라고 재확인했고 3분 내 수정 요청. 별도 댓글 목록을 제거하고 상단 관점 그룹 안에서 댓글 전체 원문·분류 이유·다섯 판단·원문 위치를 읽도록 통합했다. 댓글이 있으면 댓글만 분모로 삼고, 한 관점이어도 펼친 게이지를 표시한다. 기사 인용을 댓글 개수에 섞지 않는다. 댓글이 없으면 기존 기사 속 비교 가능한 복수 관점만 표시하는 동작 유지.

AI 지침에서 댓글이 있는데 단일 관점이면 빈 배열을 반환하던 충돌 제거. 모든 댓글을 입장/명시된 이유별로 정확히 한 그룹에 배정하도록 명시하고 불명확/주제 외 의견도 추측 없이 구분한다. 프론트 opinionGroups는 댓글 ID 중복 집계를 막으며 누락된 댓글은 회색 '관점 분류 누락'으로 보존한다. 이 항목은 AI 분류 결과가 아님을 설명한다. 재분석 전 기존 응답에서도 댓글을 조용히 숨기지 않는다.

검증: frontend lint/build/check:extension/API10/feed6, backend test/bootJar 통과. 브라우저 합성 응답으로 여러 관점/단일 관점/분류 누락 및 원문 이동 확인. 그룹 함수로 기사/댓글 혼합과 중복 방지 확인. 시간 제한 내 실제 AI 재호출은 하지 않았으며 의미 분류 품질까지 실검증했다고 주장하지 않는다. 새 지침 적용은 서버 재시작+확장/기사 새로고침 후 재분석.

## 2026-11-24 원문 DOM 보존·직접 텍스트 본문·최종 리더 배치

네이버 URL https://n.news.naver.com/article/215/0001273805?cds=news_media_pc 는 article에 p 없이 텍스트/연속 br로 본문을 구성한다. 기존 contentSize가 p/li만 세어 article을 놓치고 body 메뉴까지 출처로 수집해 40개 상한 오류 발생. 공통 DOM 순회로 inline 텍스트와 block 경계/빈 줄을 나누며, 본문으로 선택한 구간의 링크만 수집한다. 사이트 도메인/ID 분기 없음. 실제 본문 출처가 40개를 넘으면 여전히 명시적 실패하며 근거를 조용히 자르지 않는다.

전자신문 실제 실행 DOM에서는 광고 div가 p 안에 삽입됐다. outerHTML을 서버 HTML 파서가 재파싱하면서 p가 조기 종료돼 마지막 인용 대신 광고 문단이 추출되고 selector도 어긋났다. 업로드는 <!--scrollfact-dom-v1--> + XMLSerializer로 브라우저 DOM을 보존하고 서버는 이 버전만 Jsoup XML 파서로 읽는다. 일반 HTML 입력은 기존 HTML 파서 유지. 본문 순회는 중첩 block 앞뒤 텍스트를 버리지 않으며, 단일 br/공백 정규화를 프론트와 통일했다. 동일 부모 내 구간 인덱스가 달라지면 원문이 정확히 한 번 일치할 때만 재연결한다. 유사 문장으로 추측해 연결하지 않는다. 숨김·폼 입력·스크립트 텍스트 제거 유지.

사용자 최종 UI 지시: 타이틀은 기존 ‘현재 문단’ 디자인 유지. 기사 맥락 해설을 맨 위, ‘이 문단을 살펴보면’의 다섯 분류/구절/이유/출처를 다음, 선택 원문은 맨 아래 ‘원문 읽기’로 기본 접힘. 문단을 바꾸면 접힘 상태로 시작. 문단 이동은 작은 기존 버튼. 문단 강조는 옅은 파란 사각 배경+왼쪽 세로선 유지, 범위 overlay도 동일한 흰 바탕 합성색으로 조정.

react-markdown + remark-gfm으로 해설/이유의 굵게·문단·목록·표를 표시한다. raw HTML/이미지 및 javascript 링크 실행 없음. 해설 속 색 표시는 checks.quote와 실제 렌더링 텍스트가 정확히 일치할 때만 적용하며 바꿔 쓴 문장의 분류를 추측하지 않는다. summary/reason에 Markdown 사용·핵심어 강조·서사 유지·빈 줄·3개 이상 사례 목록화 지침 추가. 이 지침의 새 AI 실호출은 이번 턴에 실행하지 않았으며 이전 실제 AI 결과 재생과 명시적인 합성 Markdown fixture로 화면 검증했다.

Gemini 명시적 503은 최대 6회, 전체 생성 요청/대기 예산 4분, 지수 백오프 1/2/4/8/16초+지터. 남은 시간에 맞춰 HTTP timeout을 줄인다. 취소/다른 상태/통신 실패는 임의 반복하지 않는다. 최종503에는 ‘다른 모델 선택’으로 AI 설정 직행. 자동 전환 없음, 사용자 선택 시 저장된 키 재사용. Google 가용성 문제 자체를 해결했다고 주장하지 않는다.

## 2026-11-24 AI에 의한 문단 삭제 제거 및 실서비스 경로 검증

사용자가 반복 누락과 지연을 지적. 문단 분리는 HTML 기반이며 별도 AI 분리 호출이 없었다. 누락 가능 경로는 AI auxiliary 분류를 결과에서 삭제하는 단계였다. 이를 제거해 추출한 모든 문단/순서를 결과에 보존한다. 신규 출력 kind는 body/opinion만 허용. 레거시 auxiliary도 전체 원문 보존으로 변환하며 ‘AI 해설 없음’을 표시한다. 이전 인용부호/종결어 예외만으로 보호하던 preserveAttributedSpeech는 preserveParagraphs로 대체. 기사 속 일반 문장도 보호한다. 기자 이메일만 있는 연락처 줄은 HTML 추출에서 결정적으로 제외; 일반 문장 속 이메일은 유지. 이미지 확대/텍스트 없는 링크는 출처 수집에서 제외.

실제 동일 키/모델 최소 일반2회+JSON스키마1회 HTTP200(0.9~1.4초). 새 빌드 격리 서버에 전자신문 원본 업로드→AI→결과 API 성공: 본문10/제외0/마지막 이사장 인용 포함, 전체10.37초, 입력2259/출력2911. 동일 기사 요청은 첫503(1299ms) 후 동일 설정 재시도200(7271ms). 해요체 및 앞서 생략됐던 사례 기능, 마지막 인용 보존을 실제 결과에서 확인했다. 모든 기사 품질/가용성 보장은 아니다. 기존 사용자8080 서버는 변경하지 않았으며 재시작해야 적용된다.

47개 backend 검사 중45개 통과/2개 선택적 검사생략, bootJar 성공. ## 2026-11-24 프로토타입 UI 일관성·인용 문단 보존·해설 문체

## 2026-11-24 Gemini 503 제한 재시도

## 지금 가장 중요한 방향

최신 사용자 결정은 **사람들의 의견 모아보기와 다른 사이트의 관련 의견·반론을 보여주는 경험이 중심**이라는 것이다. 원래의 자동 팩트체크·신뢰도 점수 중심 설명으로 돌아가지 않는다. 사실과 근거 확인은 이후 보조 탭에서 제공하는 방향이다.

사용자는 의견 수렴을 8명에게 했다고 설명했다. 그 피드백을 정리하면서 사용자 평론, 공통 수집 계층과 캐싱, 여러 색으로 문장 종류를 구분하는 아이디어가 나왔다. 그러나 한꺼번에 넣으면 난잡해지고 가독성이 떨어지므로 **기능을 덧붙이며 단계적으로 발전시키라**고 명확히 요청했다. 5색의 의미나 등급은 확정되지 않았다.

현재 구현 대상으로 승인한 것은 **1단계: 문장을 누르면 관련 의견과 이유를 간결하게 보여주는 데모**다. 마지막 UI 요청은 첨부된 예시처럼 **옆에 확장 프로그램 형태로 뜨게 할 것**이었다.

## 앞으로의 단계 (계획과 구현을 혼동하지 말 것)

관련 채팅에서 제안한 순서이며 1단계만 데모 구현되었다. 다음 단계를 자동으로 모두 구현하라는 상시 지시는 아니다.

2. 비슷한 의견을 이유 중심으로 묶고, 공통점·차이를 요약하며 실제 의견으로 펼쳐 보기.

## 왜 방향이 바뀌었나

원래 구상은 페이지 HTML을 서버에 보내 문단별 요약·신뢰도·근거·반대 주장을 스크롤로 읽는 것이었다. 긍정 점수, 음수 감점, 점수 없는 근거 리더 등 여러 실험을 했다. 사용자는 점수 차이의 의미를 설명하기 어렵고 AI가 정답을 단정하는 인상을 줄 수 있다는 멘토 피드백을 전했다. 과거 점수판은 비교용으로 남아 있으며 최신 방향의 확정안이 아니다.

또한 사실을 더 정확히 아는 것만으로 갈등이 줄어드는가에 대한 질문이 반복되었다. 특히 **사실에는 동의하지만 가치관·우선순위가 달라 갈등하는 경우**가 핵심 문제로 제기되었다. 따라서 상대가 중요하게 여기는 가치와 이유, 각 선택이 사람들에게 주는 부담, 공통점과 남은 차이를 읽도록 돕는 방향을 검토했다.

이는 아직 효과가 입증된 결과가 아니다. 실제 발언에서 확인되는 이유만 연결하고, 밝히지 않은 의도·양보 조건을 만들어내지 않는다. ‘반대 댓글 없음’을 ‘모두 동의함’으로 바꾸지 않고, 공감 수를 진실의 등급으로 취급하지 않는다. 건강한 소통을 의견 일치로 정의하지 않는다.

| 연결 점검 | `frontend/src/integration/`, `/integration.html` | 실제 진단 API 확인용 |
| API 클라이언트·계약 | `frontend/src/api/`, `frontend/docs/backend-api.md` | gzip 업로드·폴링·취소·결과 검증 |
| 백엔드 | `backend/ScrollFact/` | Spring Boot, SQLite, 비동기 분석 작업 |

## AI와 백엔드의 정확한 상태

HTML gzip 업로드, 문단 파싱, 공개 출처 수집, 작업 상태·결과 조회, 취소·SQLite 저장은 구현되어 있다. `diagnostic` 모드는 AI 없이 연결을 점검한다.

실제 요약·점수 평가 제공자는 미설정이다. 기본 분석 모드는 제공자가 없으면 `503 evaluator_unconfigured`를 반환한다. `AnalysisEvaluator` 구현 또는 HTTP 어댑터가 필요하다. `SCROLLFACT_EVALUATOR_URL`은 OpenAI/Gemini 원래 API URL을 그대로 넣는 칸이 아니라 **저장소의 계약을 구현한 별도 어댑터 URL**이다.

festival 의견 수집·요약 API는 이 기존 분석 계약과 아직 통합하지 않았다. 최신 제품 방향을 구현할 때 계약·데이터 모델을 검토해야 하며 단순히 키만 넣으면 완성되는 상태가 아니다. 프론트 `VITE_*` 값에는 비밀키를 넣지 않는다.

## 실행과 이어가기

Windows PowerShell 설정과 명령은 루트 `README.md`를 따른다. 먼저 `npm ci` 후 `/festival.html`을 열어 현재 범위를 파악한다. Node.js 24.x를 기준으로 안내하며 백엔드는 JDK 17 이상이 필요하다.

일반 프론트 개발 포트는 5173, 백엔드는 8080이다. 과거 채팅의 8765 정적 서버는 자동 실행되지 않는다. `coaching.html`에 포함된 연결 점검은 8081 전용 설정이므로 일반 `/integration.html`의 8080과 구분한다. 이전 Mac의 절대 경로·실행 중 서버·로컬 DB는 새 컴퓨터에 생기지 않는다.

자료를 읽은 뒤 최신 방향과 미완료 범위를 짧게 요약하고 사용자의 다음 요청에 맞춰 작업한다. 과거 코칭 문서의 비교 시험안이나 AI의 제안을 현재 합의된 일정·검증 결과로 해석하지 않는다.

2026-11-19 Mac, Node.js 24.15.0, JDK 23.0.1에서 확인. Windows 실기 실행을 확인한 것은 아니다.
